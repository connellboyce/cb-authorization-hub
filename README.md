## Overview

### OAuth2.1 Authorization Server

#### OAuth Endpoints
- **/oauth2/authorize**
  - Authorization endpoint
  - Redirects to the login page if not authenticated
  - Redirects to the client application after successful authentication
- **/oauth2/token**
  - Token endpoint
  - Exchanges authorization code for access token
  - Exchanges refresh token for new access token
- **/oauth2/jwks**
  - JSON Web Key Set endpoint
  - Provides public keys for verifying JWTs

#### Supported Grants
- Authorization Code
- Client Credentials
- Refresh Token
- On-Behalf-Of Token Exchange (Work in Progress)

#### OpenID Connect Compliant
- Supports OpenID Connect
- Provides ID Token
- Supports UserInfo endpoint (Work in Progress)

### Login Page
- Authentication
  - Username and password authentication
- Registration
  - User registration


### Developer Hub

#### Application Management
- Register a new application
- Update an application
- Delete an application
- Define scopes owned by the application

#### OAuth Client Management
- Register a new OAuth client
- Update an OAuth client
- Delete an OAuth client
- Define grants to be consumed by the OAuth client
- Define scopes to be consumed by the OAuth client

### Management API
RESTful equivalents of the Developer Hub, intended for OAuth clients acting on behalf of a developer. The `/portal` pages remain available until a replacement portal ships.

#### Authorization
Every request requires a bearer access token issued to a user who currently holds the `DEVELOPER` role. Client credentials tokens are rejected. Requests are stateless: session cookies are ignored and no CSRF token is needed.

On every request the token's signature, issuer, and expiry are validated. The user and role are re-checked in the user store, and the token must hold the scope required by the operation. Resources owned by another developer return `404`, exactly as if they did not exist.

| Scope | Grants |
|---|---|
| `urn:cb:scope:authhub:clients#read` | Read and list owned clients |
| `urn:cb:scope:authhub:clients#write` | Register, update, and delete owned clients |
| `urn:cb:scope:authhub:applications#read` | Read and list owned applications and their scopes |
| `urn:cb:scope:authhub:applications#write` | Create, update, and delete owned applications and their scopes |
| `urn:cb:scope:authhub:scopes#read` | Read the scope catalog |

#### Client Registration ([RFC7591](https://datatracker.ietf.org/doc/html/rfc7591) / [RFC7592](https://datatracker.ietf.org/doc/html/rfc7592))
- **POST /api/v1/clients**
  - Registers a client. Supply a `client_id` (1-128 characters of `A-Z a-z 0-9 . _ ~ -`, not already registered) or omit it to have one generated. The `client_secret` is always generated by the server, any supplied value is ignored, and it is returned only in this response
  - Advertised as `registration_endpoint` in `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration`
- **GET /api/v1/clients**
  - Lists the caller's clients (extension, not part of RFC 7591)
- **GET | PUT | DELETE /api/v1/clients/{client_id}**
  - Client configuration endpoint, returned as `registration_client_uri`
  - `PUT` replaces all metadata; omitted fields are reset to their defaults. A `client_secret` in the body is optional, but if present it must match the current secret
- Supported metadata: `client_name`, `redirect_uris`, `grant_types` (`authorization_code`, `client_credentials`, `refresh_token`), `response_types`, `token_endpoint_auth_method` (`client_secret_basic`, `client_secret_post`), and `scope`
- Errors use the RFC 7591 format: `{"error": "invalid_client_metadata" | "invalid_redirect_uri", "error_description": "..."}`

#### Applications and Scopes
- **GET | POST /api/v1/applications**
- **GET | PUT | DELETE /api/v1/applications/{id}**
  - Deleting an application that still defines scopes returns `409`
- **GET | POST /api/v1/applications/{id}/scopes**
- **DELETE /api/v1/applications/{id}/scopes/{scopeId}**
  - Deleting a scope assigned to any client returns `409`
- **GET /api/v1/scopes**
  - Catalog of every scope and the application that defines it
- Errors use [RFC9457](https://datatracker.ietf.org/doc/html/rfc9457) problem details (`application/problem+json`)

#### Issuer
Tokens are always issued and validated with the hardcoded issuer `https://auth.connellboyce.com`, in every environment, including local runs. It is not derived from the request's host, and every resource-server endpoint rejects tokens whose `iss` differs.

Because discovery documents are built from the issuer, a locally running hub also advertises `https://auth.connellboyce.com` endpoints in `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration`. For local testing, call the local endpoints directly (as the Bruno collection does) rather than relying on discovery.

#### Open Decisions and Known Limitations
- **Known vulnerability ([#100](https://github.com/connellboyce/cb-authorization-hub/issues/100)):** the portal and `POST /api/v1/clients` let developers choose a client's `client_id`, so it can equal a user's id. A `client_credentials` token's `sub` would then match that user. The management API rejects these tokens because it also requires the `username` claim, which only user tokens carry. Other resource servers that identify the caller from `sub` alone are still exposed until #100 is fixed.
- **Registration access tokens:** RFC 7592 expects a per-client `registration_access_token`. For now, the owning developer's user access token authorizes client configuration requests and no registration access token is issued. Whether to adopt registration access tokens is not yet decided.
- Any developer may request any registered scope. Until scope approval exists, another developer's client can block deletion of your scope, and therefore of your application.
- A scope assigned to a client in the moment between the reference check and the delete can be left orphaned.
- Deleted scope names can be reused, and tokens issued before the deletion may still carry them until they expire.
- Clients registered through the portal support both `client_secret_basic` and `client_secret_post`. The first update through the API keeps only the method sent in that update.

## References

### OAuth 2.1
The OAuth 2.1 Authorization Framework ([proposal](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1-10)) is an extension of the OAuth 2.0 standard ([RFC6749](https://datatracker.ietf.org/doc/html/rfc6749)) authorization server.

### On-Behalf-Of Grant
Also known as token exchange grant, On-Behalf-Of grant [RFC8693](https://datatracker.ietf.org/doc/html/rfc8693) is an extension of OAuth2.0 and is used to exchange a token for another token on behalf of a user. This is useful for scenarios where a client application needs to access a resource on behalf of a user, but does not have the user's credentials. Microsoft has [one such implementation](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow)
